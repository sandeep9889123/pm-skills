# Prototype and AI application evaluation

For each new task ask 5–10 material scoping questions and await the phase approval. Continue an already scoped, approved phase without another intake. Preserve user authority, claim lineage and ₹0 incremental spending. Do not install tools, call billable APIs, deploy, expose private data or perform external actions without applicable authorization. Tool unavailability means coverage incomplete / UNKNOWN.

## Define the evaluation contract

Capture the user job, audience/tenant, current authority and source versions, success/failure criteria, permitted actions, baseline/candidate configurations, observed data, label provenance, relevant slices, risk/cost constraints and decision owner. Preserve inherited claim IDs, evidence states, freshness, restrictions and contradictions. An output specification or synthetic case is not a measured result. A new quality threshold is a PROPOSAL until accepted by its owner.

## Run the workflow

1. Inspect actual outcomes and the interactions that produced them before choosing generic metrics. Keep observations, cause hypotheses and fixes separate. If available, use `eval-error-discovery`; otherwise link each observation to its trace, deduplicate tasks/exports and state sampling bias. Missing events remain unjudgeable. Do not estimate population failure rate from complaints alone.
2. Define rubric criteria and independent label instructions. If available, use `eval-annotation-guidance`. Identify the labeling unit, PASS/FAIL/UNRESOLVED criteria, current authority, reviewer and adjudication record. Treat model-produced labels as synthetic until genuinely reviewed.
3. Build the dataset manifest. Include ordinary, edge, adversarial and confirmed-failure cases. Separate representative measurement from stress tests. Deduplicate and split related conversations/documents as groups. Keep development data apart from untouched final assessment; freeze snapshots and identifiers. Read [data readiness and datasets](references/data-readiness-and-datasets.md).
4. Assign each criterion a suitable oracle: exact code/state check, domain-human review or calibrated model judgment. Prefer exact checks for schemas, permissions and observable state. Model grading needs human-label alignment, not just a convincing rationale. If available use `llm-judge-calibration`; otherwise report class-specific errors against held-out human labels, provenance and uncertainty. A grader is itself an evaluated component.
5. Compare baseline and candidate on matched frozen tasks with equivalent tools, corpus, model settings, grading and trial budgets. Preserve first outputs and errors; report changes in configuration. Distinguish code/API failures from incorrect model answers without erasing user-visible failures. Keep repetitions linked to tasks and avoid treating them as independent users. Read [comparison and regression](references/comparison-and-regression.md).
6. Evaluate RAG retrieval and generation separately: relevance at the returned rank, available relevant-evidence inventory, material-claim support, valid citations, answerability, stale/contradictory sources and access filters. Include answerable, unanswerable, contradictory, out-of-date, access-filtering, citation and prompt-injection cases. Read [RAG evaluation](references/rag-evaluation.md).
7. Evaluate agents using authorized final-state evidence as well as observable tool/action traces: tool selection, argument correctness, permissions, retries/idempotency, partial failures, loop termination, long-session state, delegation and human handoffs. A claimed completion is not a verified outcome. Read [agent evaluation](references/agent-evaluation.md).
8. Report task success, critical failures, slice results, unjudgeable/abstained cases, denominators and uncertainty alongside measured end-to-end latency and total cost per successful task. Include failed attempts, retries, retrieval/tools and review costs; identify missing components. Keep currencies and price versions explicit. Read [cost and routing](references/cost-and-routing.md).
9. For production learning, specify trace instrumentation, representative and risk-targeted review, drift checks, feedback-to-regression and an incident workflow. Separate model/quality drift from telemetry or dependency failure. Read [operations](references/operations.md). Test UI interaction, navigation, empty/loading/error/recovery, role/tenant isolation, responsive/a11y constraints and API behavior within declared scope; use [AI UX research](references/ai-ux-research.md) for user evidence.

## Deliver the review packet

Provide the evaluation contract, dataset/split manifest, rubric and label provenance, grader audit, run/configuration fingerprints, per-slice comparison, cost/latency accounting, failed examples, coverage gaps and owner-defined gate results. Use [measurement records](references/measurement-records.md). Status each check PASS, FAIL, BLOCKED or NOT_RUN with evidence and environment. A mock result does not prove real AI behavior; static scans do not prove production safety. Release blockers: unapproved action, paid action, fabricated test, hidden P0 defect, context loss. A strong average cannot override a critical permission failure.

Keep deployment approval with the human owner. Preserve earlier failed evidence when changing a rubric, case or model, and state what additional evidence could resolve blockers. Do not invent sample sizes, benchmark wins or universal pass rates.
